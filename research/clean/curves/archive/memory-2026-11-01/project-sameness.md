## Principle (Shonu, 2026-10-18)
After I said "warm up" before the demo and the HP chat took 40-75 s to open: "there isn't a single part of this workflow which we should accept, hey, this is a crappy computer and therefore it's going to be slow." The Cale equation applies to every moment around Cale. The bar is that it feels the SAME on many computers; he prefers a spectrum with shifting bounds per computer, not a yardstick.
- Why: Cale exists so local AI feels the same on weak and strong hardware. The only accepted blocker for the HP is the missing small sizes (later Matryoshka research).
- Apply: judge each moment by sameness across computers first (gap rule), then a perception sanity bound; two times per moment: feedback and usable. Never list "warm up first" as a demo step. If slow because of AI size, use a smaller size, not a longer wait. The window never waits for the AI to load. Text above reading speed is waste ([[feedback-cale-design-rules]] overshoot). Install goal: Cale's own work under 5 min, plus a second number from double-click to first chat reply. Chat gets a "Quicker to Smarter" slider, no technical words. Plan: `~/.claude/plans/okay-overall-i-think-streamed-sutton.md`.

## Decisions (2026-10-18)
- Hosting a prepared (repacked) model file on Hugging Face: ALLOWED (live: parkingsoman/cale-gemma-3n-E4B-it-GGUF; install skips repack; upload needs Shonu's HF login, never enter tokens myself). Code signing: NO. Keep chat running / start Cale at login: NO (fixes must not depend on a resident program).
- Why: he does not accept "same circumstances, one computer is slower" as fate; a CPU ratio (3-7x) does not hold for every step. Only the intelligence boundary is accepted. Cut work at the moment a person waits (fewer files, processes, lazy init), never keep things running.
- Ship-prepared rule (principle 19, `docs/PRINCIPLES.md`): any preparation that does not depend on the device is done ahead and shipped ready (hosted), never repeated at install. Before adding an install step ask "does the result differ per computer?" Only hardware test and engine choice run at install. Why: repeating work costs most on the weakest computer.
- Fixed-time tests (2026-10-18): no "text first, rest later" download (would not apply to the future model, confuses people). Calibration runs a FIXED TIME, not fixed work (a fixed-work test took 12 s on Mac, 311 s on HP). A reading is a window: at least 2 s and 32 tokens, at most 7 s, after a settling step (`cale/tuning.py`, constants `docs/CONSTANTS.md`). Never add a fixed-work probe. Check tuning changes with `scripts/tune_check.py` and `scripts/predict_check.py` on BOTH computers. A slower computer gets a less exact reading, never a longer test; noise only slows a run, so read from the faster intervals and repeat a window with a stall. Causes measured first (`scripts/machine_probe.py`): internet equal (1.0x), one CPU thread 7x slower, small files 28-100x slower (two virus scanners). Levers: fewer files, less work at open (`docs/research/startup-gap.md`).
